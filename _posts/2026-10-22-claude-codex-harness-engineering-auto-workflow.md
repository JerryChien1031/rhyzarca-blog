### 一、從一次交接看問題：程式寫好了，為什麼工程還沒完成？

先看一個教學情境。Claude Code 正在調整資料匯入模組，Codex 準備替同一個模組補測試。兩邊都能讀取 Repository，也各自知道自己的任務。Claude 回報「實作完成」後，Codex 對當時讀到的檔案執行測試，得到成功結果。幾秒後，前一個工作程序才把最後一次變更寫回磁碟。這時候兩份回覆都可能出自善意，但「測試通過」已經無法證明最新版本正確。

若主控又恰好遇到工具逾時，問題會再多一層：前一位寫者究竟沒啟動、仍在執行，還是已寫入卻沒有送回結果？重派可能造成重複副作用；直接交給下一位寫者，可能讓兩個程序同時修改檔案；宣布失敗，也可能丟掉一份已經完成的產物。這個例子不是本文的實測產品需求，而是用來說明多代理工程中共同存在的時間差。

要接住這些時間差，需要的就是**代理執行環境工程（Harness Engineering）**：把模型的判斷接到工具、狀態、資源協調、驗證及恢復機制。提示詞可以要求 Agent「不要覆蓋別人的工作」，卻不能憑文字完成跨程序互斥；聊天紀錄可以保存「打算派工」，卻不能代替原生平台確實受理執行的回執。

因此，**自主工作流（Auto Workflow）**的目標應該定義得比「自動產生程式碼」更完整：使用者交付目標、驗收條件與授權邊界，主協調者自行選擇必要方法，完成實作、測試、修復與結案。**只交付目標的驗收（Goal-Only）**則刻意拿掉人類提供的角色順序與逐步操作劇本，用來觀察系統能否承擔這些工程決策。

自主性仍受授權約束。使用者可以授權修改功能，卻保留部署、權限設定或破壞性操作的裁決權。系統必須區分「目前可以繼續做什麼」與「需要新的合法入口才能做什麼」。否則，一次權限拒絕很容易被錯誤理解成應該改用另一種身分嘗試。

本文的實測日期與數字來自提供的技術草稿及其限定工程案例，涵蓋至 2026 年 10 月 19 日；本次撰稿未重新執行那些私有測試。以下會把歷史觀測、通用設計推導與教學示例分開標示。官方文件用來確認平台介面，不是這些私有測試結果的證明。

### 二、先拆責任：一位主協調者，兩個原生執行平台

跨平台架構最先要解決的不是如何傳話，而是誰負責決定下一步。本文採用**主協調者（PRIMARY Coordinator）**負責整合目標、工作相依、方法調整與結案；**原生工作者（Native Worker）**則是實際由各平台角色機制啟動、具有工具執行紀錄的工作實例。單一任務只有一位有效 PRIMARY，專業工作仍可在相依及資源條件允許時並行。

這個安排避免了兩個決策中心各自認為自己有權結案。假設 Claude Worker 發現測試需要調整，它應回傳觀測與建議，由 PRIMARY 判斷是否改變工作圖；不應在另一邊偷偷建立第二套工程目標。共同契約讓兩端對「怎樣算完成」有一致理解，原生平台則各自保有自己的工具、會話與能力限制。

![單一 Codex 主協調者連接本端 Worker、持久化工作圖及自製 MCP 橋接器，再由橋接器啟動 Claude CLI 原生 Worker](/assets/images/posts/2026-10-22-claude-codex-harness-engineering-auto-workflow_2.png)

可以將這套系統理解成幾個彼此交接、但不能互相代言的元件：

| 元件 | 它掌握的事實或決策 | 必須另外取得的證據 |
| --- | --- | --- |
| PRIMARY Coordinator | 使用者目標、工作相依、方法取捨與結案判斷 | 原生執行結果、有效授權、固定產物的驗收證據 |
| 原生 Agent 與技能（Skills） | 領域判斷、探索、實作、審查與測試方法 | 是否真的啟動、實際可用工具及執行能力 |

| 寫入認領輔助程式（File Claim Helper） | 合作協議中的寫入持有人及借還狀態 | OS 是否允許寫入、持有人自述是否符合原生紀錄 |
| 獨立審查者／測試者（Reviewer／Tester） | 固定候選版本與原始證據是否支持驗收 | 該候選版本是否就是最後交付版本 |

</div>

這裡的「原生」有實際意義。在完成跨端測試的方向中，Codex 經專案自製的橋接程序啟動 Claude CLI，再由 Claude 的原生機制執行指定 Worker。它不是 Codex 在回覆中模仿 Claude 的語氣，也不是把兩個角色名稱寫進同一段 Prompt 就算完成。

操作介面與執行入口也需要分開。桌面應用（Desktop）是人類與主會話互動的地方；命令列介面（Command-Line Interface，CLI）可以建立另一個具有自身載入條件的會話；MCP Server 是對外提供工具的程序。設定檔存在、主會話看得到工具、對端程序已啟動、產物已通過驗收，是四個不同的觀測點。每跨過一個觀測點，都應留下對應回執，而不是依賴前一位 Agent 的推測。

### 三、共用契約如何落地：共享語意，保留平台自己的角色機制

共用契約要解決的是語意一致性。例如「實作完成」是否包含讀回產物？「測試成功」必須綁定哪個版本？工具逾時之後，誰有權決定重試？如果 Claude 與 Codex 各自讀到一套不同規則，即使工具彼此連通，交接仍會失真。

本案例的做法是讓共同工程原則有單一入口，再由平台設定展開。`AGENTS.md` 可承載共同目標、變更範圍、驗收與恢復規則；Claude 的專案入口 `CLAUDE.md` 明確引入適用契約，並配合自己的角色定義；Codex 則由實際載入的指示與專案設定承接。不能假設 Claude 會因為某份 `AGENTS.md` 存在，就自動取得所有共同規則，也不能假設已開啟的每個會話都同步套用新設定。

下面是**教學用的責任配置圖，不是本案例可直接部署的完整目錄**。`task-state/` 是用來解說持久化資料位置的通用名稱；兩端必須各自確認檔案確實載入。

```text
workspace/
├── AGENTS.md              共用工程契約
├── CLAUDE.md              Claude 平台入口及契約引用
├── .claude/agents/        Claude 原生角色定義
├── .codex/config.toml     Codex 專案設定
├── .codex/agents/         Codex 專案角色定義
├── .agents/skills/        按需要載入的工作知識
└── task-state/            工作圖、證據索引與恢復資訊
```

角色檔案的語法必須尊重各平台。Claude Code 使用帶有 YAML 前置資料的 Markdown 定義子代理。以下是**依官方格式撰寫的最小教學示例**，不是私人正式角色檔；工具清單限制此角色的工具面，並不能代表所有外部程序都受它控制。[Claude Code 子代理文件](https://code.claude.com/docs/en/sub-agents)

```markdown
---
name: candidate-reviewer
description: Review a fixed candidate and report verifiable findings.
tools: Read, Grep, Glob
---

Inspect the supplied candidate version and acceptance criteria.
Report findings with evidence. Do not implement changes.
```

依撰稿時的 Codex 官方說明，專案可在 `.codex/agents/` 使用獨立 TOML 檔定義自訂角色。以下同樣是**格式教學示例**；名稱與指示由本文設計。它表達審查職責，沒有替會話建立另一個唯讀 Sandbox。[Codex 子代理文件](https://learn.chatgpt.com/docs/agent-configuration/subagents)

```toml
name = "candidate-reviewer"
description = "Inspect a fixed candidate and report evidence."
developer_instructions = """
Read the supplied candidate and acceptance criteria.
Report findings with evidence. Do not implement changes.
"""
```

原稿使用的是在專案設定中宣告角色、再指向 TOML 設定層的寫法；官方設定參考仍列有 `agents.<name>.description` 與 `agents.<name>.config_file`。這說明**共同的角色職責可以維持，平台的載入介面卻可能演進**。實作時應對照安裝版本及實際工具清單，不能把本文示例當成每個版本皆相同的安裝契約。[Codex 設定參考](https://learn.chatgpt.com/docs/config-file/config-reference)

技能負責重用工作知識，角色負責專業分工，兩者都不應暗中增加授權。這也解釋了為什麼根入口不宜無限膨脹：曾有一段工程把每次事故都追加成常駐指示，最後連文件載入上限都成為問題。較合理的分配是保留精簡、始終適用的共同契約，讓角色細節按需載入，歷史事故則作為可追溯資料保存。

這一層如何驗證？不能只檢查檔案存在。至少要從合法的原生入口啟動角色，確認它取得固定輸入、使用預期工具，並留下可核對的結果。只有如此，「Reviewer」才是一位實際執行過的工作者，而不是工作圖中一個好看的標籤。

### 四、把工程事實留在工作圖：先記意圖，再綁定真實執行

跨會話工作最大的狀態風險，是把一句回報當成一筆已發生的事實。「準備派 Builder」與「原生平台已接受 Builder」之間有時間差；「Builder 已結束」與「測試已確認這版產物」之間也有時間差。**Graph Runtime** 的價值是將這些差異持久化，讓下一個會話能從已知事實恢復，而不必讀完全部聊天再猜測進度。

一張有用的工作圖不只存節點名稱。它還需要保存工作相依、使用者驗收條件、由主控推導的中間檢查、條件修訂、輸入與產物版本、原生結果的索引，以及遇到未知狀態時尚待確認的事項。這裡的驗收條件稱為 **Acceptance Criteria（AC）**。若不知道某份測試報告究竟對應哪一版 AC、哪個候選版本，即使報告內容是 PASS，也不足以支撐結案。

以下為**概念狀態圖**，用來解釋事件順序，並非正式 Runtime 所有狀態名稱的逐字列舉：

```text
PENDING
   | 記錄派工意圖
   v
DISPATCHING
   | 原生平台受理，取得實際執行參照
   v
RUNNING
   | 收集原始結果與固定產物版本
   v
HARVESTED
   | 依有效 AC 獨立驗證
   v
VERIFIED
   | 必要條件成立，未結資源已處理
   v
CLOSED

執行中斷且結果不明 -> UNKNOWN -> 唯讀對帳及受控恢復
```

2026 年 10 月 17 日的控制圖檢查曾暴露一個缺陷，工程紀錄將它標為 **F11**：派工前的檢查點要求真實 Worker 身分與執行識別，甚至提前要求確認檔案所有權。但 Worker 尚未啟動，也還沒有提出寫入認領。一個任務因此提前填入不正確身分，另一個在啟動後才補記，兩者都不符合預期時序。

根因是狀態機在錯誤的時間要求尚不存在的資料。若只要求模型「更仔細填表」，下一輪仍會遇到相同矛盾。修復原理是將事件拆開：先保存 `dispatch_intent`，原生工具受理後記錄 `launched`，必要時再晚綁定真實身分；寫入認領則等到寫者實際需要資源時再發生。**F11 是工作圖身分及時序綁定缺陷，不是那兩項產品功能驗收失敗。**

並行更新還有另一種風險。假設兩個程序都讀到修訂 12，一個補上執行回執，另一個補上測試結果；若直接各自覆寫整張圖，後寫者可能抹掉前一筆更新。**比較後交換（Compare-and-Swap，CAS）**要求更新時帶上預期修訂，只有目前版本相符才接受；版本不同就重新讀取、整合，不能盲目重送舊快照。

```python
# 概念偽程式碼；函式皆為本文教學命名，非官方或可直接呼叫的 API。
graph = read_graph()
intent = append_event(
    "dispatch_intent", node=node, expected_revision=graph.revision
)

execution = launch_native_worker(scoped_input)
# 工具實際受理後，才有 execution.ref；不可事先猜造。
latest = read_graph()
append_event(
    "launched", node=node, execution_ref=execution.ref,
    expected_revision=latest.revision
)

result = collect_original_result(execution.ref)
if result.is_unknown:
    record_unknown_for_reconciliation(node, execution.ref)
else:
    candidate = freeze_artifact_version(result)
    verify_against_ac(candidate, effective_ac_revision)
```

這段示意省略了儲存、錯誤處理與重試實作，不能憑它宣稱取得完整交易保證。尤其原生 Worker 已啟動、但 `launched` 尚未寫入就崩潰的窗口，仍需要 Transport 的既有紀錄與原生回執協助對帳。CAS 能防止工作圖更新互相覆蓋，不能替外部程序提供「剛好執行一次」保證。

2026 年 10 月 18 日，這套工程的 **Core Contract C1–C7 正式整合進 Runtime**。這是該案例的整合里程碑，不是 Claude、Codex 或 MCP 的官方標準。本文只解釋原稿能支持的狀態、修訂與證據原理，不替未公開的 C1–C7 逐條杜撰內容。Graph 管理紀錄一致性，平台提供執行事實，獨立驗證者檢查產物；三者分工後，狀態欄中的 PASS 才有可追溯意義。

### 五、MCP Native Transport：讓派工可追蹤，也讓重試有邊界

工作圖知道下一個節點應該執行，並不表示它能直接啟動另一個平台。這裡用到**模型情境協定（Model Context Protocol，MCP）**作為工具連接方式。就標準輸入／輸出（stdio）傳輸而言，用戶端啟動 MCP Server 子程序，雙方經標準串流交換協定訊息；這個標準定義傳訊方式，沒有替應用程式決定誰是 PRIMARY、誰能修改檔案。[MCP stdio 規格](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/stdio)

本案例在這條通道上加了一層**專案自製的 Native Transport**。Codex 主控呼叫其工具，Transport 驗證派工資料、保存紀錄，再從合法入口啟動 Claude CLI 原生 Worker。MCP 的傳輸層與專案的原生派工橋接層是不同層次；後者的工具語意是應用設計，不是協定自帶的跨平台 Agent 功能。

原稿以以下名稱說明應用介面。**這些是本案例的自製工具職責，不是 OpenAI 與 Anthropic 共同提供的內建 API**：

<div markdown="1" style="overflow-x: auto;">
<div markdown="1" style="min-width: 720px;">

| 自製工具 | 它應完成的工作 | 不能順帶宣稱的結果 |
| --- | --- | --- |
| `dispatch` | 核對限定範圍、保存派工意圖、嘗試啟動原生 Worker | 產品已完成或已通過驗收 |
| `collect` | 收集同一執行實例的原始輸出、產物與終態 | 其他子程序一定全部停止 |
| `status` | 回傳有證據支持的已知狀態 | 沒有回覆就代表沒有副作用 |
| `reconcile` | 依停止、副作用、認領釋放與覆核證據處理未知前手 | 逾時後可以無條件再派一位寫者 |

</div>
</div>

一份派工包至少需要讓接收者知道：這是哪個任務與節點、哪一次嘗試、指定角色是誰、可讀寫哪些資源、輸入版本是什麼、適用授權從哪裡來。輸入以內容雜湊綁定，才能避免「Reviewer 原本要審 A，實際卻讀到後來的 B」。原生執行識別則等受理後再綁定，不能由主控預填一個看似完整的值。

真正棘手的是重試。回到開頭的情境：Claude Worker 可能已經寫完檔案，只是 `collect` 沒有把結果交回主控。此時「工具逾時」描述的是觀測失敗，不能證明外部操作未發生。同一節點的同一次嘗試應回查既有紀錄；若原結果不明，先確認程序終態、產物副作用及認領狀態。這是避免重複操作的應用層責任，不能因為 MCP 連線恢復就跳過。

因此，Transport 保持狹窄職責很重要。它可以回答某次原生執行的已知終態，不能自封為另一位 Planner，也不應自行修改產品 AC 或擴大權限。主控是否能結案，仍要看固定版本的驗收結果、未結資源與使用者授權。通道的成功只是其中一筆證據。

### 六、File Write Claim：協調寫入窗口，不能冒充作業系統強制鎖

即使派工與結果都能追蹤，共享工作樹仍可能被兩位 Worker 同時修改。聊天中的「我準備寫這個檔案」不夠可靠：訊息可能延遲，另一個會話也未必看得到。這時需要**檔案寫入認領（File Write Claim）**，由確定性的 Helper 管理合作成員的寫入窗口。

這是一種**合作式互斥機制**。遵守協議的寫者在動手前先認領；已有有效持有人時，Helper 拒絕另一位寫者。它無法攔截所有編輯器、Shell、第三方程序或未經 Helper 的寫入途徑，不能稱為作業系統的全域強制鎖。

要理解它的能力，必須把幾種常被混在一起的控制分開：

<div markdown="1" style="overflow-x: auto;">
<div markdown="1" style="min-width: 720px;">

| 機制 | 回答的問題 | 適用邊界 |
| --- | --- | --- |
| 存取控制清單（Access Control List，ACL） | OS 對此執行身分是否允許指定存取？ | 依實際權杖、物件權限與作業系統語意判定 |
| 執行沙箱（Sandbox） | 此執行上下文能接觸哪些路徑、工具或網路？ | 視平台、工具及執行入口而定 |
| 平台核准（Platform Approval） | 這項工具動作是否獲得平台要求的核准？ | 不因契約文字或 Claim 自動取得 |
| 操作守衛／事件掛鉤（Guard／Hook） | 已掛接入口的這次操作是否符合規則？ | 覆蓋範圍及是否具有否決能力，取決於實作與模式 |
| File Claim Helper | 合作協議中，目前誰取得此資源的寫入窗口？ | 不授予 OS 權限，也不約束所有旁路寫者 |

</div>
</div>

這張表不是通用的固定執行順序。一次寫入可能同時受多層限制，任一層通過都不能替另一層背書。即使 Claim 有效，Sandbox 仍可能拒絕；即使平台允許工具呼叫，也不能推斷已有正確的工程認領。若 Helper 以 Worker 自己的身分執行，帳本自述的 `holder` 也不是獨立身分認證，仍需核對原生工具紀錄。

正常的認領生命週期是：**借閱（Borrow）→ 寫入 → 讀回並固定產物版本 → 正式歸還（Return）→ 確認釋放 → 下一位角色接手**。它與**任務責任歸屬（Task Ownership）**不同。PRIMARY 或 Builder 可以長時間對任務負責，但寫入認領只應覆蓋當次需要修改資源的窗口。若 Builder 等 Reviewer 時一直持有認領，或要求唯讀 Reviewer 也先借到寫入權，就會把協調機制變成阻塞來源。

![Codex 與 Claude 輪流持有共享檔案認領，對端在有效持有期間遭拒，歸還後才接手的時序圖](/assets/images/posts/2026-10-22-claude-codex-harness-engineering-auto-workflow_3.png)

*圖三：互斥證據需要同時成立的持有期間、對端認領拒絕，以及拒絕前後不變的內容雜湊。圖中一個交接序列是教學示意，不能當作帳本事件總數。*

本案例的互斥驗證可用下列順序理解：Codex 先成功認領共同資源，Claude 在這段有效持有期間嘗試認領，應被 Helper 拒絕，且共享檔案內容不變；Codex 正式歸還後，Claude 才成功認領。接著交換方向：Claude 持有期間，Codex 的認領應遭拒；Claude 歸還後，Codex 能再認領、讀回並正式歸還。

拒絕必須有正確原因。單獨看到 `PermissionError`、Hook 拒絕或程序逾時，都不能算作合作式互斥通過，因為那可能只是 OS 權限不足，尚未走到認領判斷。驗收必須對照原生工具結果、有效持有時間、Borrow／Return 帳本與內容讀回，證明「因為對方正持有，所以本次認領被拒絕，且沒有造成寫入」。

2026 年 10 月 18 日的限定跨端終驗對照了 **12 組成功 Borrow／Return，以及相對應的 24 筆帳本事件**。這是成功借還的計數，**不是 12 個產品任務，也不是 24 次互斥衝突或端到端測試**。互斥是否成立，要看上述相反方向的競爭與交接證據，不能只看帳本列數。

### 七、從四種故障學恢復：每一層都要有可驗證的退出路徑

#### 1. 路徑認領遇到硬連結：拒絕新寫入，也要能處理舊持有

**失敗時保持關閉（Fail-closed）**要求在條件不足時停止危險動作。但若所有拒絕都沒有合法出口，系統就會陷入**失敗後卡死（Fail-stuck）**：保護仍在，正常工作與恢復卻一起停擺。

本案例曾遇到 Windows NTFS 的**硬連結（Hard Link）**問題：同一個實體檔案可以有多個名稱，單一路徑不足以代表完整資源。以路徑為基礎的 Helper 因此拒絕一般借閱，是可以理解的保守設計；問題是，同一條限制又套到正式歸還與維護流程。測試留下的多重名稱無法由合法持有人處理，連帳本的中間發布狀態也可能被同一規則阻斷。

修復原理是拆分操作語意：一般借閱防止新增風險，正式歸還處理既有持有，受控恢復處理特定停靠狀態，唯讀對帳提供判斷依據。恢復入口仍須限定物件與前提、保存處置證據，不能用一個「忽略所有檢查」開關取代。原稿支持這個故障與修正方向，但未提供涵蓋所有硬連結變體的測試母體，因此不應延伸宣稱此類風險已全面消失。

#### 2. 契約允許，OS 仍拒絕：ACL 修復必須同時核對能力與保全

另一段工程中，Codex 能讀取必要檔案，卻無法透過 Helper 寫入帳本。若只讀治理文件，很容易誤以為 Guard 或角色設定沒有放行。實際盤點發現，一批舊目錄關閉了 NTFS 權限繼承，新受限執行身分無法經上層目錄取得必要存取。這是實際能力缺口，增加 Prompt 不會改變 OS 的判定。

修復還遇到身分表示的接縫：某些受限身分有有效的**安全識別碼（Security Identifier，SID）**，卻沒有可解析的一般帳戶名稱。如果維修工具先強制把識別碼轉成名稱，再交給要求名稱解析的介面，操作可能在真正修改權限前就失敗。這裡公開的是身分表示與工具介面的原理，不需要公布真實識別碼、帳號或內部維修命令，讀者仍能理解根因。

更重要的是，檔案內容未變不等於安全屬性未變。一次操作後，部分安全描述元的明示與繼承權限形狀偏離預期。工程因此保留失敗紀錄，對受影響範圍作限定恢復，再與基線核對。在**指定原始快照母體上，23,187／23,187 筆保全對帳通過**。這是特定母體的保全結果，**不是修復了 23,187 個物件**，也不是全機 ACL 永久正確的證明。

後續採取更窄的必要授與，再回到正式工作根及受測入口驗證原目標。這個權限與跨端寫入工程在紀錄中稱為 **H-2**；2026 年 10 月 19 日，原工程目標完成限定的 **F1–F5** 驗收結案。同時必須保留**原 Stage1 失敗、舊 Stage2 驅動未執行**的歷史。目標後來達成，不代表舊驅動每個階段都曾成功執行，也不需要為了把舊流程塗成綠色而重新操作正式權限。本文不替原稿未逐條展開的 F1–F5 補造細項。

#### 3. Guard 看見字串，沒有看懂副作用：先找真正的寫入目標

早期一個 Guard 把「保護路徑與寫入動詞同時出現在命令文字」當成風險訊號。結果，讀取治理文件、再把分析寫到普通報告，也可能被誤判成修改治理文件。反方向也有問題：真正的寫入目標若經變數間接表示，單純字串共現未必找得到。

問題在於量測對象錯了。Guard 應辨識哪個操作會對哪個實際目標造成副作用，並對無法確認的部分保留限制；持續堆疊例外字串，只會把同一個錯誤藏進更長的規則。即使改善解析，也必須承認它只看得到已掛接的入口。官方 Hook 文件所列的事件生命週期，是理解這種適用範圍的起點，不能拿來證明自製 Guard 具備相同強制力。[Claude Code Hooks reference](https://code.claude.com/docs/en/hooks)

本案例後期 Codex 側曾使用**僅提供建議（advisory-only）**的自訂 Guard：它回傳警示，不直接否決工具請求。該時期的硬性限制仍由平台 Sandbox、Platform Approval 與 OS ACL 各自執行；File Claim 則維持合作協議內的協調責任。這個模式差異必須寫清楚，不能把所有時期的 Hook 都畫成一道全能防火牆。

#### 4. 心跳證明反客為主：確定性時間交給程序處理

為了確認兩端 Worker「仍然活著」，工程曾要求它們每隔數秒產生新證明檔，再依很短的新鮮度期限決定能否繼續。這相當於把**大型語言模型（Large Language Model，LLM）**的一次推理回合當成即時時鐘，但思考、工具呼叫、上下文整理與磁碟操作都不保證在幾秒內完成。

後果是驗證本身產生更多檔案、借還交易與逾時問題，原本想證明的共享檔案互斥反而被掩蓋。修正採取架構減法：讓確定性的 Helper 與短時間持有資源的程序承擔互斥，讓原生紀錄與正式帳本承擔結果證據，LLM 負責啟動、判斷與收集結果。完成條件應直接量測目標性質，而不是讓模型不停證明自己正在證明。

這四種故障最後回到同一個恢復原則。Worker 若為 `UNKNOWN`，超過**存活期限（Time to Live，TTL）**、沒有心跳或缺少回執，都不足以證明它已停止。可以先做唯讀查證、繼續無相依工作；但相依寫入必須等待停止、副作用、認領釋放與必要覆核的證據。**UNKNOWN 是需要保存與對帳的工程狀態，不能為了往前跑就改寫成 FAIL，再立即重派。**

### 九、Auto Workflow 的停止條件：完成使用者目標，也避免無限自我修補

當人類先寫好完整派工劇本，指定每個角色、步驟與下一次操作，Agent 最後完成任務，主要證明的是這份外部編排有效。Goal-Only 驗收刻意移除這種方法指令，才能觀察 PRIMARY 是否會自行辨識相依、選擇角色、收集證據，並在授權範圍內修復可恢復問題。

10 月 17 日的兩項 Codex 普通任務提供了一次限定觀測：CSV 與 Queue 功能驗收成立，且觀測窗內不需要使用者逐步傳送 CONTINUE。但同一輪工程也暴露自主工作流的另一種失敗：**它可能知道如何繼續，卻不知道何時足以停止。**

原稿記錄，兩項產品任務本身合計約 41 分鐘，後續 Harness 自我驗證又投入約 2 小時 44 分鐘，最後碰到平台安全拒絕。這是當次流程的時間紀錄，不是一般效能基準。它的價值在於揭露完成條件的漂移：如果每個新發現都成為本次必須修好的元件，任務就會從交付產品，轉成無限擴張的控制器維修。

解法是區分**使用者驗收條件（User AC）**與**主控推導條件（Derived AC）**。User AC 是使用者真正要求的結果，不能由主控為了方便而刪除；Derived AC 是為達成目標推導出的中間檢查。若證據顯示某個 Derived AC 過度嚴苛、量錯性質，或已被更小且等效的方法取代，可以記錄理由、修訂條件並接受必要的獨立覆核。這種修訂必須留在工作圖，不能事後偷偷降低成功標準。

例如，「測試固定候選版本」直接支撐產品正確性，不能因為工具不方便就省略；「要求 LLM 每幾秒親自刷新證明」若沒有量到真正的互斥性質，則應重新檢查設計。主控需要說明替代方法如何維持必要性質，再以測試證據確認，而不是用一句「為了效率」取消檢查。

對準備建立類似系統的團隊，可以從一個逐步擴大的最小閉環開始：先定義目標與權限，讓每端原生角色能在固定輸入下完成工作，再用真實程序驗證共享資源的借閱、拒絕、歸還及異常退出。接著加入只記錄已發生事實的持久化工作圖，最後才接入單一方向的跨平台 Transport，確認未知前手不會導致盲目重派。

當這些底座具備證據，再以普通產品需求做 Goal-Only 驗收，同時檢查產品 AC、控制圖、人工方法介入與未結資源。角色是可選用的專業能力，不是每項任務必須走完的流水線；反向主控與更多並行工作，也應在既有方向可靠後另行驗證。這樣增加複雜度，才知道每一層究竟解決了什麼問題。

### 結語：可自主推進的工程，也必須可解釋地恢復與結案

Claude Code 與 Codex 的跨平台協作，核心在於把意圖、執行、狀態、資源與證據接成一條可核對的鏈。共同契約讓兩端理解相同的完成語意；原生 Worker 提供實際執行；MCP Native Transport 承接受理與收集；Graph Runtime 保存版本化的工程事實；File Write Claim 協調合作寫者；平台與 OS 執行各自的能力限制；獨立驗證則把成功宣告綁回固定產物。

這些責任清楚後，人類才有機會退出日常的逐步派工，同時保留授權與最終責任。遇到未知時，系統能保存缺口、合法對帳；遇到權限邊界時，能指出必要入口；條件成立時，也能停止擴張工作並交付結果。

衡量這類架構，應看它是否在明確範圍內完成真實需求、留下可獨立檢查的證據，並保留失敗與修訂的因果歷史。模型、工具與平台會繼續變動，能讓工程延續的，是後來的人與 Agent 仍然可以回答：做過什麼、為什麼這樣做、目前證明到哪裡，以及下一次中斷時該從哪裡恢復。
