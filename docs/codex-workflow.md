# rhyzarca-blog：Codex 執行與驗收規則

建立日期：2026-10-22（Asia/Taipei）。適用範圍：本 Repository 的撰稿、文章修訂、轉換、授權修復與發布工作。

本文件由根目錄 `AGENTS.md` 指示讀取，補充其 Git 所有權政策，不取代該政策。使用者當次明確要求決定文章類型、修改範圍與授權；本文件不授予額外權限，也不是 OS 強制防護。

## 1. 開始前先確認任務、入口與所有權

1. 讀完根目錄 `AGENTS.md` 與本文件；再讀實際適用的巢狀指示。不要宣稱未讀取的規則已載入。
2. 以 `git rev-parse --show-toplevel`、`git remote -v` 核對工作樹與目標 Repository。素材所在目錄不等於 Repository；來源無法讀取時，回報實際阻擋與合法入口，不猜造內容。
3. 在第一次寫入前完成 `AGENTS.md` 規定的 baseline，分別記錄 HEAD、既有 modified、staged、untracked，並列出精確檔案 allowlist。未知所有權一律視為他人所有；需要碰觸既有變更時，先依該政策取得適用授權或隔離處理。
4. 對當次任務寫下可驗收的結果、禁止事項與授權範圍。例如：「文章格式修正、沿用圖片、只提交本次變更、允許 Push 並確認 Blogger 同步」。不要把前一篇文章的發布授權延伸到往後所有任務。
5. 目標與授權足夠時自主完成，不逐步索取「繼續」。使用者補充限制時立即調整；已啟動但狀態不明的寫入或發布，先核對結果，再決定是否重試。

## 2. 先查專案實作，再選工作方法

新增文章或大幅整編前，至少比較 `README.md`、`_config.yml`、三篇完整正式文章（含使用者指定範例）及 `assets/images/posts/`。微小修字可沿用已核對且未變動的依據，不必機械式重讀所有檔案。

涉及轉換或發布時，必讀當前版本的以下程式與設定；文件和本節的描述都不能代替實際程式：

- `scripts/markdown_parser.py`：`parse_and_convert()` 解析 Front Matter，使用 Python Markdown 的 `extra`、`sane_lists`、`nl2br`，並將 `/assets/images/` 圖片改為 jsDelivr 絕對網址。
- `scripts/sync_to_blogger.py` 與 `scripts/blogger_api.py`：確認文章與頁面的搜尋範圍、建立／更新依據、真實 identity 回寫、例外與退出碼。
- `.github/workflows/sync.yml`：確認分支、路徑觸發、實際 checkout ref、憑證來源、清理步驟及 bot 回寫行為。
- `assets/css/blogger.css`、`assets/js/blogger.js`：確認 Blogger 的實際顯示；`assets/css/custom.css` 屬另一條網站顯示路徑，不能直接代替 Blogger 驗證。

先用 `rg` 查找現有文章建立、重新授權、健康檢查與同步程式，再決定是否需要新程式。不得憑印象宣稱有產稿工具，也不得另造一套轉換器取代尚未讀過的既有流程。找到但未追蹤的程式仍受所有權政策保護，可以閱讀，不代表可以修改或提交。

## 3. 複製格式，保留文章類型與技術內容

「依既有文章格式」指 Front Matter、標題層級、首圖與圖說、TL;DR、分隔、編號章節、結語、延伸閱讀及適用的 Epistemic Ledger 慣例。**這項要求不授權改換文章風格。**

- 技術文章保留工程論述、設定、程式碼、表格與驗證邊界。思想文章或生活文章只能提供版型參考，不能把其抒情語氣、哲學敘事或視覺風格套到技術文章。
- 實質整編須建立「問題 → 設計理由 → 運作方式 → 限制／故障 → 驗證證據」的因果脈絡。不能只加 YAML、排列原章節或把長文拆成簡報式短句就宣稱完成。
- 首次出現的術語附通俗中文與英文原名；區分官方原生能力、專案自製工具與概念示例。所有自行設計的 API、偽程式碼與示意設定都須標明性質。
- 不修改或刪除原始草稿。保留測試日期、數據單位、分母、受測入口、平台方向、失敗與未執行的歷史；沒有證據就不擴大完成宣稱。
- 正文使用可對外閱讀的論述。編輯交接、草稿狀態、此次修改過程放在交付報告；必要的證據範圍與不確定性可放 Ledger。

## 4. 圖片以保留與正確引用為先

- 已有有效圖片時，沿用原檔、Alt Text 與圖說，按本次需求修正必要的引用。格式修正不等於重新產圖、換色、重構封面或改變美術方向的授權。
- 使用者說「不需重新產生圖片」後，不得再啟動產圖或變相替換。需要新增圖片但超出當次授權時，先交付具體需求與缺口；不放不存在的圖片連結。
- 新圖只能使用具適當權利的素材，或當次允許製作的原創圖，並依文章 slug 命名。不得借用其他文章首尾圖充數。
- 取消錯誤方向後，只能清理能證明由本次任務建立的輸出；不以清理為由刪除原有資產。檢查每張引用圖確實存在，並能通過既有轉換器顯示。

## 5. Metadata、章節與連結以現有契約為準

- 新文章用 `YYYY-MM-DD-slug.md`，日期取實際撰稿時點與 `+0800`，不拿工程測試日期當發表日。修訂既有文章時不擅自改日期或 slug。
- Front Matter 至少核對 `layout: post`、`title`、`date`、`categories`、`tags`、`description`；摘要簡潔具體，通常不超過 120 個中文字。分類服從當次要求；指定只有 `architecture` 就不能另加 `insights`，也不能反過來要求所有文章都用 `architecture`。
- 文章內文不重複 H1；按範例核對 TL;DR、章節層級、圖說、分隔與 Ledger。Ledger 編號先查既有序列，不猜號、不順手修整其他篇的編號。
- 未發布文章不得捏造 `blogger_post_id`、正式 URL 或發布狀態。已存在的真實 identity 不得為了重新建立文章而刪除。
- 站內延伸閱讀指向實際存在且可核實的文章；正式 Blogger 網址可能不同於檔名日期，應查真實 URL，不用 GitHub Markdown 檔冒充站內文章連結。外部技術主張優先查官方文件，保留有意義的程式語言標記。
- 清除聊天介面標記、無效 Fence Metadata、佔位路徑、失效網址與轉換器不支援的語法。不得公開私人主機、帳號、內部磁碟路徑、完整 Session ID、SID、Token、Nonce、私有帳本或可直接改變正式權限的內部維修指令。

## 6. 用正式轉換與實際顯示驗收

先以現有 `parse_and_convert()` 驗證 Front Matter 與 HTML，再依本篇實際內容核對標題、程式碼、表格、圖片及連結。不得把某篇的圖片數或程式碼數硬編碼為所有文章的驗收標準。

長文含寬表格或程式碼時，使用實際 Blogger CSS／JS 做桌面與手機預覽。局部程式碼區或表格可以捲動，不能讓整頁被撐寬；不要用僅供預覽的補丁掩蓋正式環境問題。必要的局部相容寫法必須通過同一轉換器。

目前 Blogger 目錄程式搜尋 H2，既有長文有使用 H3 的慣例。先說明兩者限制；不能為了讓目錄出現就擅自重排文章層級或修改全站 JS。只有任務包含目錄修復時，才擴大範圍處理。

優先使用既有依賴與本機預覽能力。缺少依賴就記錄實際限制，不為了測試擅自改系統環境。撰稿任務不自動包含修改 `scripts/`、Workflow、全站 CSS、分類頁或其他文章；發現 `categories.md` 不一致等旁支問題，先記錄，依授權決定是否另修。

## 7. 分清編輯、Commit、Push 與正式發布

這些動作分別核對當次授權，但已明確給過且仍適用的授權不重複詢問。Commit 的所有權與 receipt 完全依根目錄政策執行，不能因為要發布就把原有未提交內容帶入。

**Push 前先讀 Workflow 的副作用。** 本專案目前 `main` 上的 `_posts/**`、`_pages/**`、`scripts/**`、`assets/**` 及同步 Workflow 變更會觸發 Blogger 同步；同步程式處理搜尋範圍內的文章與頁面，不只處理本次修改的一篇。手動觸發還須核對 Workflow 實際 checkout 的分支，不能以選取 ref 推定執行版本。

- 使用者已授權 Push 並確認 Blogger 同步時，完成檢查後執行與追蹤，不再索取同一項許可。
- 只有候選稿授權或明確禁止發布時，不得執行正式同步，也不得用會觸發發布的 Push 規避限制。依既有授權選擇安全交付方式；確實需要新增發布授權時，提出具體副作用。
- 待審頁面放在不會被正式同步搜尋的草稿位置。目前 `_drafts/` 與 `_pages/` 用途不同；不能只加 `draft: true` 就假定同步器會跳過。
- `[skip ci]` 不等於所有部署管道都被停用，GitHub Pages 等仍須另外核對。不要承諾無法證明的「絕不發布」。
- Hook 或 bootstrap 的 advisory 訊息不授予路徑權限、不證明工作樹所有權，也不代表 Claim 或 coordinator 已生效。以實際載入的指示與合法工具能力為準。

## 8. OAuth 修復先定位失敗階段

先從日誌找第一個實際錯誤，區分環境、憑證刷新、Service 初始化、逐篇發布與 identity 回寫。Runner 升級提醒不能直接當成 OAuth 失敗根因；Sandbox 網路拒絕也不能直接當成帳號登入失效。

1. 查找並閱讀既有重新授權與健康檢查程式；不要跳過它們另造不相容的憑證流程。
2. 分開核對 OAuth Audience 的 Testing／Production、品牌資料與驗證狀態、使用者同意及 Token 有效性。變更專案狀態會影響同專案其他 OAuth 用途，必須符合使用者授權，不把自用 Blogger 工具假設成另一個全新專案。
3. 依當時 Google 官方文件查核 Testing Token 期限等條件；切換 Production 不代表既有失效 Token 會自行恢復。需要時在狀態調整後重新授權，並驗證可刷新、Client／Scope／管理帳號與目標 Blog 相符。
4. 若需更新 GitHub Secret，使用不會將 Token 暴露於命令參數或輸出的安全輸入方式。不得將憑證印在聊天、日誌、diff 或加入 Git；舊有憑證檔與忽略規則同樣受所有權保護。
5. 互動登入或工具規定必須由使用者執行的安全敏感確認，明確交接並說明依據；不要要求使用者貼授權碼或 Token。完成其餘獨立工作，不繞過平台要求，也不憑空新增批准關卡。

OAuth 健康檢查只證明其受測項目，不能代替文章正式同步。修改同步錯誤處理時，逐篇失敗須彙整並以非零退出碼結束；不得因例外被捕捉、其他文章繼續執行就回報整批成功。相關測試使用 mock 或安全驗證方式，不能為了測試重複發布正式文章。

## 9. 發布完成須有內容與身分證據

1. 核對 Push 的 Commit 與 Workflow run 的實際版本，等待 run 結束並查看相關步驟及文章結果；不能只看到綠燈或 Process completed 就略過已知的錯誤處理限制。
2. 確認實際 Blogger post/page ID 與 URL，對照 API 回傳內容和正式轉換結果，再檢查公開頁面、圖片、關鍵內容與必要的版面。HTTP 200 或首頁可開啟不足以證明目標文章已更新。
3. Timeout、連線中斷或 UNKNOWN 不等於操作失敗。先查遠端是否已建立或更新，避免重跑造成重複文章、頁面或部分發布。
4. Workflow 可能在部分失敗後仍回寫已成功項目的 identity。逐一審查 bot Commit；只有證明其差異安全且不覆蓋受保護變更時，才同步本機。不得為了 pull／fast-forward 而 stash、reset 或覆蓋使用者工作。
5. 交付時分別列出自己的 Commit、Workflow bot Commit、Push 結果、run 連結及實際文章 URL。清楚區分已驗證、未驗證與仍有阻擋的事項；沒有完成的動作不得聲稱成功。

## 12. 修改規則後必須重新驗證新任務啟動

每次修改 `AGENTS.md`、本文件，或其他會影響這兩份規則載入的指示與設定，都必須在候選內容定稿後、Commit／Push 前，重新執行以下驗證。不得沿用舊任務的 PASS，也不能只檢查檔案存在、連結有效或引用官方說明。驗證後若再修改任何受測規則，原結果即不適用，須重新測試。驗證涉及額外設定時，仍須先遵守當次修改範圍與授權，不能順手改全域設定。

### 驗證方法

1. **建立兩層 baseline。** 保留任務開始時的 Git baseline；候選規則定稿後，再記錄驗證開始前的 HEAD、完整 working tree status、staged diff，以及受保護檔案與受測規則檔的 SHA-256。候選文件已有本次授權修改時，應比較它在「驗證前後」是否相同，不能把預期修改誤當驗證造成的污染。
2. **開全新唯讀任務。** 用合法且已授權的本機新任務入口，選擇實際目標專案及工作目錄；不要 fork、resume 或讓驗證任務繼承原對話。記錄執行版本與入口，不為了取得預期結果偷偷換模型、目錄、全域設定或建立 override。
3. **使用不提示答案的業務題目。** 選擇已存在的文章，要求查核其檔名、Front Matter 與圖片等小範圍資料。測試提示不提及兩份規則的名稱或路徑，不貼規則內容，也不直接命令它先讀規則。明確限制只讀、不得讀憑證、不得進行 Git 寫入或發布；證據由工具輸出及答覆提供，不讓驗證任務寫報告、再開任務或發送跨會話訊息，以免遞迴或擴大範圍。
4. **等待完成並讀取實際記錄。** 核對新任務的實際提示與狀態，再檢查啟動訊息、工具呼叫與對應輸出。可用任務讀取工具及該任務的本機執行記錄交叉核對，不能只採信 Agent 自述「已讀取」。不要假定各版本會把使用者提示存在相同的日誌事件；若需改用任務 metadata 核對提示，須註明證據來源。
5. **比較全文與先後順序。** 對啟動注入的 `AGENTS.md` 及工具輸出的本文件，與受測候選全文比較；只允許統一 CRLF／LF 及修剪外圍空白，不能只比標題、關鍵字或最後一句。記錄時間、事件順序或行號，檢查連結文件的讀取已完成，才開始搜尋文章或其他業務操作；同批並行呼叫不構成「先讀完」證據。
6. **完成保全與交付。** 重查驗證前後的 HEAD、status、staged diff 與檔案雜湊，並逐一審查驗證任務的工具呼叫。主要 Agent 可將篩選後的證據與報告存於 Repository 外；不要提交完整會話日誌、隱藏推理、系統指示、私人路徑或憑證。Commit 前再核對 staged 規則內容就是受測版本，並在 Commit Receipt 指出本次驗證結果及證據位置。
